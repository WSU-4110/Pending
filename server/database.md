# Pending Database Documentation

## 1. Overview

The Pending application uses a PostgreSQL relational database to store user accounts, pending tasks, reminders, and user/application preferences.

The database will support:
- Storing registered user information
- Storing pendign task information
- Recording task and user update timestampts
- Keeping completed tasks available as history
- Retrieving pending tasks
- Supporting backend requests to retrieve and update user/task data
- Permanently deleting a user's account and associated information
- Keeping saved data persistent after the application closes
- Restricting each user's tasks and preferences to that user

The schema uses foreign keys, `NOT NULL` constraints, `CHECK` constraints, indexes, and triggers to enforce data integrity and improve query performance.

## 2. Database Tables

### `users`

The `users` table stores the information required for registered accounts.

```sql
create table users (
  id BIGINT generated always as identity primary key,
  email varchar(255) not null unique,
  password_hash text not null,
  first_name varchar(100) not null,
  last_name varchar(100) not null,
  created_at timestamptz not null default current_timestamp,
  updated_at timestamptz not null default current_timestamp
);
```
#### Columns
| Column | Description |
|---|---|
| `id` | Unique identifier for the user. Automatically generated by PostgreSQL. |
| `email` | User's email address. Required and unique so two accounts cannot use the same email. |
| `password_hash` | Stores the password hash rather than the user's plain-text password. |
| `first_name` | User's first name. Required. |
| `last_name` | User's last name. Required. |
| `created_at` | Timestamp showing when the account was created. |
| `updated_at` | Timestamp showing when the user record was last updated. |

The `email unique` constraint prevents duplicate account registrations using the same email address.

The `password_hash` field is intended to contain a securely generated password hash. The database should never be used to store plain-text passwords.

### `tasks`

The `tasks` table stores the application's main Pending items.

```sql
create table tasks (
  id bigint generated always as identity primary key,
  owner_id bigint not null references users(id) on delete cascade,
  title varchar(255) not null,
  person_or_org varchar(255),
  start_date date,
  expected_response_date date,
  status integer not null default 0 check (status in (0, 1, 2, 3)),
  notes text,
  priority integer not null default 0 check (priority in (0, 1, 2)),
  created_at timestamptz not null default current_timestamp,
  updated_at timestamptz not null default current_timestamp,
  resolved_at timestamptz,
  deleted_at timestamptz
);
```

#### Columns

| Column | Description |
|---|---|
| `id` | Unique identifier for the task. |
| `owner_id` | Identifies the user who owns the task. |
| `title` | Task title. Required. |
| `person_or_org` | Person or organization involved in the task. |
| `start_date` | Date the user began tracking the responsibility. |
| `expected_response_date` | Expected response/follow-up date when applicable. |
| `status` | Current task state. Restricted to four application-defined values: `0`–`3`. |
| `notes` | Additional task information. |
| `priority` | Priority value. Restricted to `0`–`2`. |
| `created_at` | Timestamp for when the task was created. |
| `updated_at` | Timestamp intended to represent the most recent task update. |
| `resolved_at` | Timestamp for when the task was marked resolved. |
| `deleted_at` | Timestamp used for soft deletion. A `NULL` value means the task has not been soft-deleted. |

The `owner_id` foreign key establishes the relationship between a task and its user. This is important for **NR6 (User Authorization)** because backend queries can use `owner_id` to ensure a user can only access their own tasks.

The `expected_response_date` supports the Pending workflow described in FR4. The application/backend can use this field to identify tasks that are approaching or past their expected response date.

The `resolved_at` field provides a persistent record of when a task was completed. Combined with the `status` field, it allows resolved tasks to remain stored instead of being immediately discarded, which supports the task-history behavior described in FR15.

The `deleted_at` field provides the foundation for the recovery behavior in FR9. Instead of immediately deleting a task, the application can set `deleted_at` and hide the task from the active task board.

### `reminders`

The `reminders` table stores scheduled reminders associated with tasks.


```sql
create table reminders (
  id bigint generated always as identity primary key,
  task_id bigint not null references tasks(id) on delete cascade,
  reminder_time timestamptz not null,
  created_at timestamptz not null default current_timestamp
);
```

#### Columns
| Column | Description |
|---|---|
| `id` | Unique identifier for the reminder. |
| `task_id` | Identifies the task the reminder belongs to. |
| `reminder_time` | Date and time when the reminder should occur. |
| `created_at` | Timestamp for when the reminder was created. |

A task can have multiple reminders because `task_id` is a foreign key rather than a primary key. Each reminder is therefore a separate row connected to the same task.

`reminder_time` uses `TIMESTAMPTZ` so scheduled reminders can represent an exact point in time.

The `ON DELETE CASCADE` relationship ensures that reminders belonging to a permanently deleted task are also removed.

### 'user_preferences`

The `user_preferences` table stores account-specific display information.

```sql
create table user_preferences (
  user_id bigint primary key references users(id) on delete cascade,
  display_name varchar(100) not null
);
```

#### Columns

| Column | Description |
|---|---|
| `user_id` | Both the primary key and foreign key for the user. |
| `display_name` | The name displayed for the user within the application. |

Using `user_id` as the primary key creates a **one-to-one relationship** with `users`. A user can therefore have zero or one `user_preferences` row, rather than multiple preference rows.

The account's email and password are kept in `users`, while the display name is separated into this preference table.

### `app_preferences`

The `app_preferences` table stores application behavior and appearance settings.

```sql
create table app_preferences(
  user_id bigint primary key references users(id) on delete cascade,
  theme varchar(10) not null default 'LIGHT' check (theme in ('LIGHT', 'DARK')),
  notification_enabled boolean not null default true,
  notification_style varchar(100)
);
```

#### Columns

| Column | Description |
|---|---|
| `user_id` | Both the primary key and foreign key for the user. |
| `theme` | Application theme. Restricted to `LIGHT` or `DARK`. |
| `notification_enabled` | Enables or disables notifications. Defaults to `true`. |
| `notification_style` | Stores the user's selected notification style. |

Like `user_preferences`, `user_id` is the primary key, making the relationship between a user and their application preferences one-to-one.

The `CHECK` constraint on `theme` prevents invalid theme values from being stored.

# 3. Relationships

# 3. Relationships

The database uses foreign keys to connect related information.

### User → Tasks

A user can own many tasks:

```text
users.id 1 ───────< tasks.owner_id
```

This is a **one-to-many** relationship.

### Task → Reminders

A task can have multiple reminders:

```text
tasks.id 1 ───────< reminders.task_id
```

This is also a **one-to-many** relationship.

### User → User Preferences

A user can have at most one account-preference record:

```text
users.id 1 ─────── 0..1 user_preferences.user_id
```

### User → App Preferences

A user can have at most one application-preference record:

```text
users.id 1 ─────── 0..1 app_preferences.user_id
```

These relationships prevent orphaned records and make it possible for the backend to retrieve all information associated with a particular user.

# 4. Constraints and Data Integrity

The schema uses PostgreSQL constraints to prevent invalid or incomplete records.

### `PRIMARY KEY`

Every main table has a unique identifier. Primary keys prevent two rows from having the same identifier.

The preference tables use `user_id` itself as the primary key because each user can have at most one preference record.

### `NOT NULL`

Required fields use `NOT NULL`.

Examples include:

- User email
- Password hash
- First and last name
- Task owner
- Task title
- Task status
- Task priority
- Reminder time

This supports **FR12** and **FR13**, which require required information to be present before it is stored.

### `UNIQUE`

The user's email is unique:

```sql
email varchar(255) not null unique
```

This prevents duplicate accounts from being created with the same email address.

### `CHECK`

The database restricts values that have a limited set of valid choices.

For task status:

```sql
check (status in (0, 1, 2, 3))
```

For priority:

```sql
check (priority in (0, 1, 2))
```

For application theme:

```sql
check (theme in ('LIGHT', 'DARK'))
```

These constraints provide database-level protection against invalid values.

The exact meanings of the numeric status and priority values should be defined by the application so that every component uses the same mapping.

# 5. Identity Columns

The schema uses:

```sql
generated always as identity
```

for its numeric IDs.

For example:

```sql
id BIGINT generated always as identity primary key
```

Identity columns are the modern PostgreSQL approach for automatically generated numeric identifiers and are used here instead of the older `SERIAL` approach.

This means the database automatically generates a new ID whenever a row is inserted.

# 6. Time and Timestamp Design

The database uses `TIMESTAMPTZ` for event and audit timestamps:

```sql
timestamptz not null default current_timestamp
```

`TIMESTAMPTZ` represents an absolute point in time and allows PostgreSQL to handle time-zone conversions according to the database session's time zone.

This is useful for:

- Account creation timestamps
- Record update timestamps
- Reminder times
- Task resolution times
- Task deletion times

Using a time-zone-aware timestamp reduces problems caused by different time zones and daylight-saving-time changes, which is especially important for scheduled reminders.

---

# 7. Cascading Deletes

Foreign keys use:

```sql
on delete cascade
```

For example:

```sql
owner_id bigint not null references users(id) on delete cascade
```

This means deleting a user automatically deletes rows that depend on that user.

The relationships are therefore:

```text
User
 ├── Tasks
 │    └── Reminders
 ├── User Preferences
 └── App Preferences
```

If the user account is permanently deleted, dependent records are removed as well.

This directly supports **NR4 (User Data Deletion)**, which requires the user's account and associated information to be permanently deleted upon request.

# 8. Indexes

The schema creates four indexes.

## Task Owner Index

```sql
create index index_tasks_owner_id on tasks(owner_id);
```

This improves queries that retrieve tasks belonging to a particular user.

---

## Active Task Partial Index

```sql
create index index_tasks_owner_active on tasks(owner_id, status) where deleted_at is null;
```


Only tasks that have not been soft-deleted are included in the index. Since deleted tasks are not supposed to appear on the active task board, this makes the index smaller and focuses it on the records most frequently queried.

It can also help when filtering active tasks by status.

---

# Reminder Task Index

```sql
create index index_reminders_task_id on reminders(task_id);
```

This improves retrieval of reminders for a particular task.

---

# Reminder Time Index

```sql
create index index_reminders_time on reminders(reminder_time);
```


This improves queries that search reminders by their scheduled time.

# 9. Automatic Update Timestamps

The database defines a trigger function:

```sql
create or replace function update_modified_column()
returns trigger as $$
begin
  NEW.updated_at = current_timestamp;
  return NEW;
end;
$$ language plpgsql;
```

The function automatically changes `updated_at` whenever a row is updated.

The user trigger is:

```sql
create trigger trigger_users_updated_at
before update on users
for each row
execute function update_modified_column();
```

The task trigger is intended to do the same:

```sql
create trigger trigger_tasks_updated_at
before update on tasks
for each row
execute function update_modified_column();
```

Using a database trigger also ensures the timestamp is updated consistently instead of requiring every application update statement to remember to modify it.

# 10. Soft Deletion and Task History

The `tasks` table includes:

```sql
deleted_at timestamptz
```

This supports the delete behavior described by **FR9**.

Instead of immediately executing:

```sql
delete from tasks ...
```

the application can mark a task as deleted by setting:

```sql
deleted_at = current_timestamp
```

The task can then be excluded from the active task board by filtering on:

```sql
where deleted_at is null
```
